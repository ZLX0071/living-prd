# 产品定型流程

这是交互 PRD 的必经前置，已完整内置原 `PM-Make` 的意图、流程和模板，不依赖外部 Skill。

若入口是已有 Demo 代码，先执行 [code-demo-intake.md](code-demo-intake.md)，再用代码证据填充本流程；代码无法说明的产品动机、目标用户、价值和成功指标仍需向用户澄清。

## 推进方法

1. 读取 `shaping/00-competitive-analysis.md` 与 `shaping/00-intake.md` 至 `shaping/05-open-questions.md`，把用户已给出的信息写入，不知道的保留 `[待确认: ...]`。这些文件都已在底座“产品研究与参考”分组中，更新后应能实时查看。
2. 每轮只问 3–5 个当前最能降低不确定性的问题，不让用户填整张表。
3. 先收敛一句话定位，再确认用户与场景，用 JTBD 检查真实动机，然后拆 MVP，最后落到页面、流程、规则、数据和权限。
4. 每轮后同步更新相关 shaping 文件和待确认问题。冲突信息单列，不自行裁决。
5. 达到通过标准时，先向用户展示定型摘要并等待确认。确认后追加到 `shaping/06-shaped-brief.md`，不覆盖历史版本。

## 必问维度

- **产品一句话**：为谁，在什么场景，解决什么高价值问题，带来什么进展。
- **目标用户**：主用户、决策者、影响者、被影响者。
- **JTBD**：情境、动机、期望进展，以及功能/情感/社会任务。
- **当前替代方案**：现在的做法、痛点、切换阻力。
- **竞品与差异**：直接/间接竞品、可借鉴与应避免、差异化机会，沉淀在 `shaping/00-competitive-analysis.md` 并回写定位与 MVP 范围。
- **MVP 边界**：必须有、暂缓、明确不做。
- **核心流程**：入口、主路径、关键分支、失败/空/等待/超时/取消/审批状态。
- **页面与信息架构**：页面清单、职责、主要信息和跳转关系。
- **业务规则**：状态、权限、数据来源、约束、成功指标。
- **视觉输入**：品牌规范、设计系统、参考产品或明确授权使用默认规范。

## 高价值问题库

### 定位与场景

- 这个产品希望用户在什么场景下使用？
- 如果只能解决一个问题，最应解决什么？
- 用户为什么不继续使用现有方式？

### JTBD 与四力

- 当用户遇到什么情境时，会想找新方案？
- 用户要完成的实际进展是什么？希望感觉更省心、专业、安全还是高效？谁会评价结果？
- Push：现状中最难受的触发点是什么？
- Pull：新方案最吸引人的收益是什么？
- Anxiety：用户最担心什么失败、成本或风险？
- Habit：用户为什么会沿用旧方式？

### 边界、流程与规则

- 没有哪 3 个能力，产品就无法成立？哪些只是增强？哪些本期明确不做？
- 用户从哪里进入，正常完成路径是什么？哪些节点会失败、回退、取消、超时或需要审批？
- 哪些角色能看、能改、能审批、能导出？
- 哪些数据由用户填写，哪些来自系统或外部来源？

## 通过标准

同时满足后才能进入板块计划：

- 产品定位可在 1–2 句中准确表达。
- 至少一个核心用户、一个核心场景、一条主流程明确。
- MVP 有明确的“做 / 暂缓 / 不做 / 待确认”。
- 竞品分析结论已回写定位差异与 MVP 范围，未确认项集中到待确认问题。
- 关键业务规则、权限、数据对象未被含糊带过。
- 未确认内容集中在 `shaping/05-open-questions.md`，且不影响即将规划的核心范围。
- 视觉输入已明确为“用户规范”或“默认简洁规范”。
