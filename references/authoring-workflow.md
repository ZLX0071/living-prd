# 模块化作业与审核

## G1 板块计划

在 `prd/00-plan.md` 中给出：

| 字段 | 要求 |
| --- | --- |
| 模块 ID / 名称 | 稳定 ID，名称可改 |
| 目标 / 用户任务 | 该模块为谁完成什么 |
| 范围边界 | 包含、不包含、待确认 |
| 依赖 | 数据、权限、前置模块、公共组件/状态 |
| 交付物 | Markdown、原型页、状态展示页、标注 |
| 全局关系 | 入口、出口、跨模块跳转、对旧关系的影响 |
| 审核标准 | 可观察的通过条件 |

计划模块在 manifest 中固定使用 `id: plan`、`kind: process`、`navNumber: "00"` 和 `hidden: false`。它只服务于作业过程，不是最终 PRD 正文；可在任意时刻由底座隐藏或重新显示，最终交付前必须设为 `hidden: true`。

计划顺序默认是：产品定义与目标 → 用户与需求分析 → 用户故事与旅程 → 核心主路径 → 分支/边界模块 → 全局收口。前三项即使内容已在 shaping 中讨论，也必须作为独立正式 PRD 板块交付。组件与状态是进入功能模块前要完成的参考基线，不列入正式 PRD 顺序。展示计划后停止，等用户审核；不要在同一轮生成全部模块。

## G2 PRD 基础分析

将已确认的 shaping 结论提炼为面向产品、设计、研发、测试等最终读者的正式文档。不要原样搬运 `[待确认]`，也不要只链接 shaping 文件。至少交付：

1. **产品定义与目标**（`prd/01-product-definition.md`）：一句话定义、问题/机会、目标与非目标、价值主张、范围与边界、成功指标、约束、假设和未决问题。
2. **用户与需求分析**（`prd/02-users-and-needs.md`）：用户角色/分群、使用情境、现有替代方案、痛点、JTBD/需求陈述、证据与置信度、需求优先级、边缘用户和可访问性考虑。
3. **用户故事与旅程**（`prd/03-user-stories-and-journey.md`）：故事地图或主题、原子用户故事及 Given/When/Then 验收标准、现状旅程、目标旅程、关键触点、情绪/痛点/机会、失败与恢复路径。
4. **数据与北极星指标**（`prd/04-metrics-and-north-star.md`）：北极星指标定义与口径、指标树、护栏指标、反例（明确不作为成功依据的虚荣指标）、数据来源与埋点需求。指标应可追溯到用户价值和关键功能模块；无数据时写明测量计划，不得虚构基线。在进入 G4 功能模块前确认，避免功能交付与价值脱节。

四个板块应互相可追溯：需求指向用户证据，用户故事指向需求，指标指向用户价值与关键故事，旅程节点指向故事/功能模块。若产品确实不存在某一项，写明"不适用"的理由，不能直接删掉标题或模块。

## G3 设计参考基线：DESIGN、组件与状态

- 先完成并请用户确认 `reference/DESIGN.md`，manifest 使用 `kind: reference` 和 `navNumber: R1`。Demo 入口遵循 [code-demo-intake.md](code-demo-intake.md)：有用户规范就登记权威来源并检查实现差异；没有才从代码还原。
- 组件与状态保存为 `reference/components-and-states.md`，manifest 使用 `kind: reference` 和 `navNumber: R2`；两份资料与全部 shaping 文档一起显示在“产品研究与参考”，不得计入正式 PRD 序号。
- 写明全局导航、页框、表单控件、反馈、弹层、列表/详情等共享组件的用途、变体、交互和禁用条件。
- 定义 loading、empty、error、disabled、permission-denied、offline、success 等跨模块状态，按产品实际需要取舍。
- 用 `prototypes/pages/components.html` 展示公共组件；用 `prototypes/pages/states.html` 并列展示关键状态。
- 共享实现放在 `prototypes/shared/`，模块页只做组合与少量局部扩展。

## G4 单模块作业包

每轮先读取全部 manifest、已完成模块的摘要和当前全局流程，再交付：

1. **PRD**：目标、范围、角色/权限、前置、原子功能条目、业务规则、数据、异常/空/加载状态、非功能约束、验收标准、未决问题。
2. **原型**：可操作主路径，使用真实感示例数据，每个可见跳转都能实际操作。
3. **状态页**：将难以在一次演示中并列看到的多状态组合展示，便于设计师接力。
4. **标注**：只标注需要解释的交互/规则，标题简短，内容应能追溯到 PRD 小节。优先给目标元素设置稳定的 `id` 或 `data-annotation-anchor` 并写入 `target`；否则必须在底座固定视口中用“添加标注”实际点击落点，禁止根据 HTML 或截图猜坐标。
5. **关系与画布回归**：检查所有现有页面的入口和出口；更改错误、过时或重复的边，而不是只添加当前页的边。关系确认后在全局画布执行“自动排列”，再拖拽微调；不要自行估算一组页面坐标。
6. **基础回写**：若出现新公共组件或状态，同一作业包更新 G3 产物；若功能结论改变用户需求、故事或旅程，也同步回写 G2 对应板块。

交付时摘要列出“新增 / 修改 / 未决 / 影响的旧关系 / 验证结果”，然后停止等待模块审核。

## G5 全局收口

- manifest 中每个模块的 Markdown 和每个页面文件都存在。
- 每个功能页都归属模块，多状态功能有状态展示页。
- 画布中无孤立主路径页、无指向不存在页面的关系、无与真实点击行为矛盾的跳转。
- 画布页面之间至少保留 40px 间隔，页面卡片不得重叠；所有关系箭头和标签均可见，箭头不得完全被页面卡片覆盖。运行自动排列后仍需做一次浏览器目视检查。
- 标注不遮挡关键控件，序号稳定，内容可追溯。
- 逐条点击右侧标注列表做定位回归：目标元素应滚动到可见区域，气泡应落在目标边缘或留白处而非正文中心；默认关闭标注时页面不得残留气泡。
- PC/手机页在各自固定视口下无裁切和比例失真。
- 所有原型的共享页框、主色、字体、间距和交互反馈一致。
- 编辑器的 Markdown、标注和 HTML 修改都能落盘，刷新后保留。
- “文档与原型”页的三种阅读状态均正常：纯 PRD、约 2:1 的原型/PRD 对照、展开原型并用悬浮审阅栏查看 PRD 或标注；切换状态不丢失当前模块和原型页。
- 每个正式模块都能导出 Markdown，且所有对应原型截图可打开；shaping/reference 可按资料包导出，process 不导出。至少抽查一张截图与浏览器原型并排对比，确认背景、字体、颜色、边框、布局和组件状态均已保留，而不只是检查 PNG 文件存在。另抽查“复制飞书 / Notion Markdown”：Mermaid 已折叠为节点说明、页面标注转为表格，粘贴到协作文档可直接阅读。
- `plan` 模块仍保留 `prd/00-plan.md` 和审核记录，但 manifest 中为 `kind: process`、`navNumber: "00"`、`hidden: true`；最终目录、默认阅读路径和正式导出均不出现该过程产物。
- 产品定义、用户与需求分析、用户故事与旅程三个正式基础板块均存在；不得用 shaping 文件或板块计划替代，且内容已反映最终确认结论。
- 竞品分析（S0）与 7 份常规 shaping 文档（S1–S7）及组件/状态参考资料均可从“产品研究与参考”访问；它们不占正式 PRD 的 `01...` 序号。
- Demo 入口还需检查代码证据文档可访问，所有正式结论有代码证据或用户确认；`DESIGN.md` 已区分观察事实、候选规范、建议修订和设计债务。
